# Phase 2 接客ルール・環境の実装

更新日：2026-09-05 / シミュレーター版：0.2.0

本書は接客環境の初期実装の記録。続く[離散化・Q学習の実装](Phase2_QLearning.md)では
学習用の`bootstrap_action_mask`を追加し、保存・比較評価まで実装済み。

今回の範囲は、飽き・切り替え効果、単一接客用Gymnasium環境、報酬内訳、境界条件テスト。
Q学習と学習済み方策の評価は次の実装単位とする。

## 暫定の接客ルール

`config/default.json` に以下を追加した。確定した製品仕様ではない。

| 設定 | 既定値 | 意味 |
|---|---:|---|
| boredom_free_actions | 1 | 同種類を続けても飽きが発生しない回数 |
| boredom_decay | 0.15 | 以後の1回ごとの満足倍率減少 |
| boredom_min_multiplier | 0.4 | 満足倍率の下限 |
| switch_min_streak | 2 | 切り替えボーナスに必要な直前種類の連続回数 |
| switch_bonus | 4 | 条件を満たして別種類へ切り替えた際の追加満足の基準値 |

種類はねこじゃらし／なでなでの2つ。同じ種類内の速度変更では連続回数をリセットしない。
休む行動は直前の交流種類・連続回数を保持する。客が変わると履歴を初期化する。
直前行動（休むを含む）と直前の交流種類は別フィールドで保持する。

正の基本効果に対しては次式を使う。

```text
飽き倍率 = max(下限, 1 - 減少係数 × max(0, 今回を含む連続回数 - 猶予回数))
満足効果 = 行動の基本効果 × 客の好み × 飽き倍率
         + 条件を満たす切り替え時のボーナス × 切り替え先への好み
```

負の効果は飽きで軽減せず、負または0の基本効果には切り替えボーナスを付けない。
満足を0〜目標に制限した後の実増分をイベントと報酬に使う。
`boredom_decay=0`、`switch_bonus=0` で追加効果を無効にできる。

この補正は `core/interaction.py` に置き、`SimulationCore` が利用する。
`CatInteractionEnv` も同じcoreを動かすため、体力回復・特別成功・会計・閉店は二重実装しない。
行動ログには飽き倍率、切り替えボーナス、連続回数、実際の体力消費量を追加した。

## Gymnasium接客環境

接客環境だけに任意依存のGymnasiumとNumPyが必要。営業CLIの標準ライブラリ構成は維持する。
今回の検証環境はPython 3.12.9、Gymnasium 1.3.0、NumPy 2.5.2。

```bash
venv/bin/python -m pip install -r requirements-env.txt
venv/bin/python -m unittest discover -s tests -v
venv/bin/python -m cat_cafe_sim.envs --seed 42
```

環境APIの使用例：

```python
from cat_cafe_sim.envs import CatInteractionEnv

env = CatInteractionEnv()
observation, info = env.reset(seed=42, options={"preferences": (1, 1)})
env.action_space.seed(42)  # 行動サンプリングの乱数は環境と別に指定
while True:
    action = env.action_space.sample(mask=info["action_mask"])
    observation, reward, terminated, truncated, info = env.step(action)
    if terminated or truncated:
        break
env.close()
```

1エピソードは猫1匹と新規客1人の接客。resetは時間を進めず、最初のstepで来店・着席・猫行動を処理する。
環境では元設定の来店列をtick 0の1人に置き換え、待機列の容量を最低1にする。
その他のゲームルールは渡された設定を使用する。
resetの`preferences`は実験側から与える非公開条件。省略時はコンストラクターの設定に戻る。
現段階ではランダム客生成を行わないため、同一設定・行動列ではseedを変えても接客結果は同じ。

- 行動空間：`Discrete(7)`。6交流行動＋休む。
- 観測：満足・体力・気力を0〜1にした3要素配列、直前行動、直前交流種類、連続回数、
  残り営業時間、今回最初の行動・初来店・猫との初対面の各フラグ。
- 行動前の符号：直前行動は7、交流種類は2。交流種類0はねこじゃらし、1はなでなで。
- 好み・来店予定・乱数状態は観測に含めない。好みは観測できないため部分観測の問題となる。
- `info`：8項目の報酬内訳、会計内訳、退店理由、元のゲーム指標、イベント、行動マスク。
- 接客中は7行動がすべて有効。終端後のマスクはすべて0で、次のstepにはresetが必要。
- 成功、不満、閉店は`terminated=True`。通常の閉店に失敗報酬や不満を付けない。
- `CatInteractionEnv(max_steps=...)` による外部上限は`truncated=True`。
  打ち切りで退店や会計を捏造しない。同時に本来の終了も起きた場合は本来の終了を優先する。
- 行動空間外の入力はValueErrorとし、状態を更新しない。営業coreの無効店長コマンドとは別契約。

[Gymnasium Env仕様](https://gymnasium.farama.org/api/env/)と
[時間制限の説明](https://gymnasium.farama.org/tutorials/gymnasium_basics/handling_time_limits/)に沿って実装した。

## 猫の報酬

`config/cat_rewards.json` に料金・満足補正とは独立して係数を保存する。
正の係数を設定し、消費・不満・失敗・時間の項目は計算時に負として扱う。

| 項目 | 係数 | 計算対象 |
|---|---:|---|
| satisfaction | 1 | 符号付きの実際の満足増分 |
| success | 30 | 成功退店1回 |
| perfect | 10 | 特別成功1回（成功報酬に追加） |
| stamina | 0.1 | 実際に消費した体力。回復による相殺をしない |
| spirit | 0.2 | 回復で実際に使った気力 |
| discontent | 5 | 今回接客の退店時不満増分 |
| failure | 30 | 不満退店1回 |
| time | 0.5 | 猫行動1tick |

`reward`は常に内訳の合計。成功時の不要な気力回復がないこと、負の満足増分も負報酬となることを検証した。
今回は新規客の1接客のみなので、退店時不満はその接客で生じた増分に一致する。
将来途中の待ち時間不満などを追加する場合は、イベント単位の増分として拡張する。

## 検証結果と診断

36件のテストが成功。既存14件の回帰検証を含む。
Gymnasiumの`check_env`、観測空間の範囲、同seed・同操作列の再現、
営業coreと環境の状態・イベント一致、終了優先順位、気力の境界、報酬内訳を確認した。
営業CLIのseed 42は従来どおり売上920・満足退店5・不満退店1。0.2.0で保存した営業ログも再生一致した。

`venv/bin/python -m cat_cafe_sim.envs --seed 42` は5行動列×3種類の好みを診断し、
設定・依存バージョン・報酬係数・結果を `reports/interaction_baselines.json` に保存する。
非公開の好みは実験レポートにのみ明示する。以下は好み(1, 1)の結果。

| 行動列 | 退店 | 接客tick | 気力消費 | 売上 | 合計報酬 |
|---|---|---:|---:|---:|---:|
| 普通ねこじゃらし連打 | 成功 | 9 | 30 | 190 | 106.5 |
| 普通速度の2種類を交互 | 成功 | 6 | 0 | 160 | 119.5 |
| 各種類2回ずつの固定ループ | 成功 | 6 | 0 | 160 | 119.0 |
| ねこじゃらしの速度を循環 | 成功 | 10 | 30 | 200 | 104.2 |
| 休むのみ | 閉店 | 40 | 0 | 400 | -20.0 |

**休み続ける行動の売上が高くなる問題を確認した。** 時間課金が続く原ルールによるもので、
猫報酬を下げても利益目的の店長が滞在を引き延ばす動機は残る。
この結果を理由に無断で最大滞在時間などのゲームルールは追加せず、
資料にある滞在上限・満足不足による不満の比較候補として残す。
単一接客の診断であり、1日全体の回転率や常連離脱を含めた最適性は判断していない。

交互連打では切り替えボーナスは発生しないが、全条件で固定ループが不利になることを保証する設計ではない。
好み(0, 2)ではねこじゃらし連打が不満退店となり、客条件による結果の変化も確認した。
これらは固定行動列の診断であり、学習済み方策の性能評価ではない。

## 互換性と次の作業

ログ項目とゲームルールを変更したため版を0.2.0に更新した。0.1.0のログは再生ツールが
バージョン不一致として拒否する。旧ログを上書きせず、新版で別名のログを生成する。
Phase 1の状況文書は0.1.0時点の記録として保存する。

次はQ学習用の離散化と状態数の測定。今回の観測は連続値を含むため、そのままQ表の直積にはしない。
履歴を必要以上に増やさずに区間化し、非公開の好みの扱いと状態集約による情報損失を確認する。
その後にQ学習、モデル保存・再読み込み、学習・調整・最終評価の条件分離、
Random・固定方策との比較を追加する。GUI・複数日経営・店長学習は今回の範囲外。
