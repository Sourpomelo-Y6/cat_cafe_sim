# 長期営業のバランス検証

検証日：2026-09-15

## 比較条件

現在の通常営業ルールを変更せず、3方針×seed 0・1・2の9試行を、それぞれ100日実行する。
日数には休業日を含める。出勤可能な猫がいない日は、全方針で休業する。

| 方針ID | 内容 |
|---|---|
| all_work | 健康な猫を全員出勤させる |
| rotating_rest | 猫ID順の5日周期で毎日1匹を休養。その他の健康な猫を出勤させる |
| fatigue_closure | 健康な猫の最大疲労が60以上なら全店休業。それ未満なら健康な猫を全員出勤させる |

テスト用猫5匹（ミケ・タマ・ソラ・コハク・ムギ）、2席、40tick営業、来店予定0・6・12・18・24・30tickを共通にする。
猫の個性、交流方策、料金、疲労・病気係数は既定設定のまま。所持金・親しみ・疲労は各試行で初期化する。
来客予定と交流方策は決定的で、この比較でseedによる差が出るのは発症判定。
ランダムな交流IDは一致しなくても、同じ条件・seedのゲーム上の集計は再現する。

## 測定方法

`cat_cafe_sim.long_term_evaluation` が独立した一時ディレクトリに関係データを作る。
プレイヤーの `saves/` は使用しない。自動割り当てで営業し、日次結果から集計する。

療養は営業開始時に病気の猫を1匹につき1匹日と数える。発症当日は療養日数に数えない。
100日目に発症して将来必要になる療養は、100日間の実績には含めない。
発症回数には同じ猫の再発も含める。

1・25・50・100日終了後の翌日準備状態で、セーブ容量・保存時間・読み込み時間を測定する。
保存と再開は同じ状態を参照する別セッションで測り、営業を続けるセッションにはチェックポイントを関連付けない。
保存・読み込み後の全状態と日次比較が一致することを確認する。
100日の処理時間は、保存再開せず連続して営業した場合の値で、GUI描画や700msの待機時間は含まない。
保存再開後の関係照合を毎操作で行う経路はこの処理時間に含まれないため、実際の再開後プレイを同じ速度とみなさない。
時間は同環境での実測値であり、専有CPUで保証されたベンチマークではない。

## 結果

9試行・合計900日を完了。表は3seedの平均（括弧内は最小〜最大）。金額はゲーム内資金。
各seedの集計・測定環境・共通設定は [集計JSON](Results/LongTermCafeEvaluation.json) に保存した。

| 指標／100日 | 全猫出勤 | 毎日1匹の交代休養 | 疲労60以上で休業 |
|---|---:|---:|---:|
| 総売上 | 102,313（101,300〜104,110） | 100,197（98,920〜101,250） | 59,670 |
| 営業日数 | 99.3 | 98.0 | 51.0 |
| 休業日数 | 0.7 | 2.0 | 49.0 |
| 営業日あたり売上 | 1,030.1 | 1,022.5 | 1,170.0 |
| 発症回数 | 114.3（108〜119） | 91.3（89〜94） | 0 |
| 療養の延べ匹日 | 225.3（212〜235） | 180.3（176〜184） | 0 |
| 療養割合（500匹日中） | 45.1％ | 36.1％ | 0％ |
| 閉店時の平均疲労 | 75.1 | 68.9 | 26.3 |
| 最大疲労 | 100 | 100 | 60 |
| 親しみ変化の合計 | +894.3 | +901.7 | +351.0 |

営業日あたり売上は、各試行の総売上÷営業日数を計算してから平均した。
疲労休業は全seedで営業・休業・交流結果が同じだった。疲労が安全閾値を超えず発症抽選による差が出なかったためで、3回の独立したランダムな健康結果を得たわけではない。

交代休養は全猫出勤より総売上が約2.1％低く、療養が約20.0％少ない。
休養の効果はあるが、5匹×100日の延べ日数の36.1％が療養で接客できないため、毎日1匹を固定順で休ませるだけでは負担が大きい。
一方、疲労休業では発症を避けられたものの、ほぼ半分の日が休業になり総売上は約41.7％減った。
営業日あたりの売上は高くても、暦日全体では減収になる。現行条件では、全店休業と全猫出勤の間を埋める個別の休養方針を次に検証する価値がある。

### 保存容量と処理時間

容量は十進MB（1 MB＝1,000,000 bytes）。セーブ本体には関係データのコピーも含まれる。
「関係データ」は別ファイルの実容量であり、合計のディスク使用量を見る場合は両方を足す。

| 測定値（3seed平均） | 全猫出勤 | 交代休養 | 疲労休業 |
|---|---:|---:|---:|
| 1日終了時セーブ MB | 0.032 | 0.032 | 0.032 |
| 25日終了時セーブ MB | 0.456 | 0.439 | 0.308 |
| 50日終了時セーブ MB | 0.887 | 0.868 | 0.572 |
| 100日終了時セーブ MB | 1.734 | 1.718 | 1.116 |
| 100日終了時関係データ MB | 0.542 | 0.535 | 0.296 |
| 100日終了時の保存 秒 | 0.212 | 0.226 | 0.140 |
| 100日終了時の読み込み 秒 | 0.284 | 0.267 | 0.179 |
| 100日分の営業処理 秒 | 175.65 | 177.49 | 64.42 |
| 最初の10日分の営業処理 秒 | 4.27 | 4.37 | 2.35 |
| 最後の10日分の営業処理 秒 | 31.66 | 33.16 | 11.01 |

セーブ容量は今回の範囲では日数とともにおおむね直線的に増え、100日で約1〜2 MBだった。
一方、全猫出勤・交代休養では最後の10日間の処理時間が最初の約7〜8倍になった。
保存容量の軽量化後も、長期営業の処理負荷は別の課題として残る。
休業方針は接客と操作数が少ないため、短い処理時間だけをもって実装が高速化したとは判断しない。

## 再実行

```bash
venv/bin/python -m cat_cafe_sim.long_term_evaluation \
  --days 100 --seeds 0 1 2 --output reports/long_term
```

各試行のJSONに使用設定・猫の個性・日次値・集計・保存測定を保存し、CSVにも日次値を出力する。
`summary.json` に全試行の集計と測定環境をまとめる。`reports/` はGit管理対象外。

## 結果を読むときの制約

- 自動割り当ては体力が高い猫を優先し、同じ体力では猫ID順に選ぶ。疲労や直近の出勤回数は考慮しない。
- 交代休養は暦日で順番を決める。その日の休養対象が既に病気でも、代わりに別の健康な猫を休ませることはしない。
- 疲労による休業は朝の健康な猫だけを見て判断する。営業中に閾値を超える場合や、休養で回復しても閾値を超えている猫は、閉店時に発症しうる。発症ゼロを保証する方針ではない。
- 発症回数だけでなく、休業日を含む総売上、営業日あたりの売上、延べ療養日数を併記する。療養割合の分母は5匹×100日＝500匹日。
- 家賃・治療費・常連離れなどの損失は未実装で、今回の売上だけからゲーム全体の最適解や成功条件は決めない。
- 3seedと既定の猫・来客数に限った比較であり、別の編成・割り当て方・混雑度にも成立する結論とはしない。

## 次に試す調整案（未適用）

1. **疲労を考慮した出勤・割り当てを先に比較する。** 今回の交代休養は固定順なので、疲労の高い猫を優先して休ませる方針や、健康な猫が十分いる日の2匹休養を比較する。全店休業を減らしながら個体の負担を下げられるかを確認する。
2. **休養日の回復量20に対して30・40を個別に試す。** 現行では疲労100から2日療養しても60までしか下がらず、復帰後の接客で再び発症域に入る。回復量を増やしたとき、全猫出勤まで有利になりすぎないかも確認する。これらの値は次回の測定候補であり、推奨値として確定していない。
3. **必要なら接客1tickあたりの疲労1を0.75・0.5で比較する。** 回復量変更と同時に変えず、それぞれの影響を分ける。発症率だけを下げる案は後に回し、まず休養で疲労を維持できるかを見る。
4. **性能は別途プロファイルする。** 操作ごとに `record_digest` が過去の日次結果・交流成果を含む状態を処理し、関係保存も全体を読み書きしている。履歴量に応じた時間増加の候補だが、今回の計測だけで処理別の寄与は断定しない。保存再開後の `check_link` を含めて測ってから、過去の確定記録の再処理を減らす設計を検討する。

次回も同じ100日・3seedで総売上、療養割合、休業日数を比較する。発症ゼロだけを成功条件にせず、営業を継続しながら予防的な休養が役立つかを判断する。
今回、疲労・回復・病気・料金・自動割り当てのゲームルールは変更していない。

## 検証

- 3方針×3seed×100日を完了し、各試行で所持金と日次売上の合計、未保存成果がないことを確認。
- 36か所（9試行×4測定日）で保存・読み込み後の状態と日次比較の一致を確認。
- `venv/bin/python -m unittest discover -s tests`：289件中260件成功、GUIの29件はスキップ。
- 追加テストは方針の境界条件（病気の猫を除外・全猫療養・疲労閾値・交代順）と、同条件での集計再現・出力・保存確認を検証する。
