# 個性ごとの成功経路と反応方策の診断

2026-09-12追記：[交流の目的・終了・成果の見直し](HumanToCatInteractionPurpose.md)を整理した。
本書の「成功」は旧来の暫定的な両側特別行動の発動条件を指し、好感度や交流全体の良さを意味しない。
低体力からの達成は必須要件ではない。実行ルールはまだ変更していない。


更新日：2026-09-12 / 対象：単独交流ルール版3

## 結論

個性既知の探索では、5個性×開始体力100／20の10条件中9条件で成功経路を発見し、再生一致を確認した。
前回の固定方策で成功0件だった「距離を大切にする猫」も、体力100で11tick、体力20で20tickの成功経路がある。
この結果から、その個性自体を弱めたり好みを均一化したりする変更は行わない。

中立・体力20は探索幅128と512の両方で未発見。ただし幅制限により候補を捨てており、不可能の証明ではない。
公開反応だけを使う改善候補も1つ比較したが、追加条件で資金が下がったため既定方策への採用は見送った。
ゲームルール・暫定値・試遊画面・既定方策は変更していない。

## 1. 探索方法と解釈

`evaluation.reachability`を追加した。実際の版3coreを分岐実行し、有効な全動作と全変更先を展開する。
終了判定や行動効果を探索用に二重実装しない。初期coreと分岐同士の状態・記録の独立性をテストした。

各層で同一の公開状態を厳密に重複排除し、幅128まで保持する。浮動小数点の丸めによる状態併合はしない。
同じ探索中は個性・ルールが固定であり、coreの将来に影響する動的状態はすべて状態キーに含まれる。
両ゲージの発動資格への進捗と体力を評価し、種類・発動済み側・体力区間ごとに候補を残す。
1条件の展開上限は250,000手。最初に成功を発見した層で、資金・残体力の順に経路を選んで止める。

これは非公開の個性を知り、分岐後の結果を試せる診断用探索。人間の初見プレイや反応だけの方策の性能ではない。
探索で個性や内部スコアを使えることと、それを実際の操作方策へ渡すことは区別する。
比較用の既存responsive方策には公開観測と公開の発動閾値だけを渡し、個性や先の結果を渡さない。

成功経路は存在の証拠になるが、今回の探索では最短手数・最大資金・最小消耗を保証しない。
JSONの`complete`は探索終了層まで幅・展開上限による切り捨てがなかったことを示す。
今回の全条件ではfalse。成功後の全経路まで調べ終わったという意味ではない。
未発見時のログは評価値の高かった途中または終了経路で、成功の証拠でも最善の失敗経路でもない。

これは選ばれた経路の説明であり、すべての経路に同じ制約があると断定するものではない。

### 観測できた難しさ

- 通常開始では、個性ごとに異なる種類や強さで成功できた。中立の経路は消費体力84、甘えん坊は25だった。
  速く成功する経路が消耗も少ないとは限らない。
- 低体力では、開始時体力20以下だと好みに合っていてもけだるさで関心増分0になる。
  停止で20を超えた後のadaptは、直前のけだるい反応により低消費の穏やかな動作になる。
  甘えん坊や繊細な猫では、この強さの好みも進捗に寄与する。
- 見つかった低体力の成功経路は停止を5〜11回使用した。20tick中に回復・種類変更・発動を収める必要がある。
  距離を大切にする猫は最終tickで成功し、時間の余裕がなかった。
- 同じ分類の飽きは種類名を変えるだけでは消えず、分類変更と好みの両方を考える必要がある。
- 既存responsiveは通常交流にdirectだけを使う。今回の探索で有効だったadaptやintenseの組み合わせを表現できない。

好み・飽き・体力・時間の影響は実行ログと既存式から説明した。各係数を別々に変える因果比較は今回行っていない。
全動作は探索対象だが、発見経路でfeintが使われなかったことは、feintが常に無用という証明ではない。

### 距離を大切にする猫の成功例

体力100では、トンネルと声かけを組み合わせて11tickで同時発動できる。

```bash
python3 -m cat_cafe_sim.human_cat_demo run --rules 3 \
  --preset '距離を大切にする猫' \
  --actions switch:tunnel intense direct direct switch:voice direct direct switch:tunnel direct direct connect \
  --output reports/distance_cat_success.json
```

この列は個性既知の探索から得た例で、他の猫への汎用方策ではない。

## 3. 改善候補を1つ比較

候補は「既存responsiveがdirectを選ぶ場面で、直前反応がlistlessならadaptに変える」だけ。
閾値・種類変更・connect優先・低体力時の停止は据え置き。ルールや猫の個性を変えず、公開反応の使い方だけを変える。
`evaluation.reactive_adapt`に比較用として置き、GUIや既定方策には組み込まない。

既存5個性×体力100／20は診断に使用済みの10条件。
候補評価前に`config/type_reactive_evaluation.json`へ3つの追加個性×体力35／70の6条件を固定した。
追加個性は従来5プリセットとは別の値。評価後の追加調整・候補の再選択は行っていない。

| 条件 | 方策 | 成功 | 平均資金 |
|---|---|---:|---:|
| 診断用10条件 | 既存responsive | 3 / 10 | 60.00 |
| 診断用10条件 | adapt候補 | 4 / 10 | 65.00 |
| 追加6条件 | 既存responsive | 2 / 6 | 58.33 |
| 追加6条件 | adapt候補 | 2 / 6 | 50.00 |

診断用の改善は繊細な猫・体力20の時間切れ／資金50から成功／100への変化。
追加条件では「変化を好む慎重派」・体力70が時間切れ／50から時間切れ／0に低下した。
adaptの低消費だけで常に有利になるわけではなく、進捗と発動時刻の影響も受ける。
この小さな比較から汎用的な改善は確認できず、候補は採用を見送る。
追加条件も今後は結果を見た条件として扱い、未使用評価とは呼ばない。

## 4. 再現手順・成果物・検証

```bash
# 個性既知の探索と、公開反応方策の比較
python3 -m cat_cafe_sim.evaluation.reachability
# 唯一未発見だった条件の追加探索
python3 -m cat_cafe_sim.evaluation.reachability --preset 中立 --stamina 20 \
  --width 512 --output reports/type_reachability_neutral_wide.json
# 単一の方策候補を比較
python3 -m cat_cafe_sim.evaluation.reactive_adapt
venv/bin/python -m unittest discover -s tests
```

探索上限は`--max-expansions`、探索幅は`--width`で指定できる。
設定は`--config`、絞り込みは`--preset`と`--stamina`を使う。

- `reports/type_reachability.json` / `.md`：基本10条件の探索統計・行動列・反応方策比較。
- `reports/type_reachability_neutral_wide.json` / `.md`：追加探索1条件。
- `reports/type_reactive_adapt.json`：診断用・追加条件の方策比較。
- 各同名ディレクトリ：再生確認したログ。基本探索20、追加探索2、候補比較32、計54ログ。

探索JSONには設定とそのSHA-256、探索幅・上限・展開数・切り捨て数・重複数・成功発見の有無を保存する。
各ログには実際の個性とルールを保存し、レポートだけから結果を捏造しない。
生成レポートはGit管理外。設定、分析コード、テスト、本書の結果を管理する。

通常テスト150件成功、今回変更していない画面専用4件はスキップ。
追加9件で全変更先、分岐の独立性、再現性、成功経路の再生、探索上限と完全探索の区別、
上限直前に見つけた成功の保持、終端入力、候補の変更範囲、追加条件の分離とログ再生を確認した。

診断時点では記憶を使う方策と追加探索を次の候補としていたが、2026-09-12時点で保留した。
先に交流の目的・終了・成果を整理する。中立・低体力の未発見は必須修正要件としない。
