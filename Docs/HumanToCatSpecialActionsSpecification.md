# テンションと特別行動：初回実装用の暫定仕様

2026-09-12追記：[交流の目的・終了・成果の見直し](HumanToCatInteractionPurpose.md)を整理した。
本書の「成功」は旧来の暫定的な両側特別行動の発動条件を指し、好感度や交流全体の良さを意味しない。
低体力からの達成は必須要件ではない。実行ルールはまだ変更していない。

ユーザー指定の「80以上で消費して使用可能」「100以上で次回強制発動」「同時発動で資金増加」は維持する。
以下の消費量・増減量・ボーナス額・猫方策・終了条件は、今回置く暫定値であり、バランス検証済みではない。
本書は版2／3の実装時に使用した仕様記録。今後の目的・終了の見直しは上記の整理を参照する。既存ルール版1とその比較記録は変更しない。

## 1. ゲージと初期状態

| 項目 | 初期値 | 範囲・扱い |
|---|---:|---|
| お客のテンション `tension` | 0 | 0〜100。更新ごとに範囲内へ制限 |
| 猫の関心 `engagement` | 0 | 0〜100。更新ごとに範囲内へ制限 |
| お客の強制予約 `connect_pending` | false | テンション100到達後、次の有効tickで心をつかむ |
| 猫の強制予約 `open_up_pending` | false | 関心100到達後、次の有効tickで心を開く |
| 特別行動ボーナス累計 `bonus_funds` | 0 | この交流の獲得額。営業の財布とはまだ接続しない |
| 心をつかむ／心を開くの発動回数 | 各0 | 成功判定と診断に使用 |
| 同時発動回数 | 0 | ボーナス診断に使用 |

100を超えた分は切り捨てる。例えば95に12加算すると100となり、実増分5・超過7を記録する。
任意発動の閾値は80、強制予約の閾値は100、発動時の消費量は**固定80**とする。
80で発動すると0、100で発動すると20が残る。消費後も関心やテンションを別ゲージへ移さない。
両ゲージと予約は試遊画面・公開観測に表示する。猫の好みは引き続き非公開観測の対象。
初回実装では通常開始は両ゲージ0。境界テスト用に初期ゲージを指定する場合は予約を初期値から導出し、手入力で矛盾させない。

体力・開始体力・残り時間・好み・通常行動の基本効果は版1を引き継ぐ。
テンションの自然減少は追加せず、下記の反応と特別行動によってのみ変動する。

## 2. 通常行動によるテンション変動

人が`direct`、`adapt`、`intense`、`feint`を実行した場合、通常ルールで計算した猫の反応から変動量を決める。
関心の増分・体力コスト・飽きは版1の計算を使う。

| 通常反応 | テンション変動 |
|---|---:|
| 熱心に応じる `enthusiastic` | +20 |
| 好意的に応じる `favorable` | +12 |
| 普通に応じる `neutral` | +6 |
| 戸惑う `confused` | −4 |
| けだるそうにする `listless` | −6 |
| そっぽを向く `turn_away` | −8 |

`pause`と`switch`のテンション変動は0。通常反応が表示されても、この表による増減は適用しない。
停止だけではどちらのゲージも増えず、体力回復と時間消費だけが起きる。
特別行動のゲージ効果は次節で処理し、通常反応によるテンション加算と二重に適用しない。

## 3. 両側の行動選択

### お客側：心をつかむ `connect`

予約がなければ、開始時テンション80以上のときに通常6行動に加えて選べる。
予約があれば、そのtickのお客側の有効行動は`connect`のみ。
GUIは「次の行動：心をつかむ」と表示し、ボタンで1tick進める。自動で時間を進めない。
APIで予約中に別行動を指定した場合は、暗黙の置換ではなく無更新の入力エラーにする。
猫側は独立して予約を処理するため、人側が通常行動を選んだtickでも心を開ける。

### 猫側：心を開く `open_up`

初回は固定方策とし、人が猫側の発動を直接操作する機能や猫の学習は追加しない。
判定は**人の今回の選択を読む前の、同じtick開始時の公開状態**から行う。

1. 猫の予約があれば強制発動。
2. 予約がなくても関心80以上で、次のいずれかなら任意発動：お客のテンション80以上、残り時間1tick、体力20以下。
3. それ以外は通常反応を返し、次の機会を待つ。

テンション80以上なら、お客が同時発動を選べる機会になる。ただし猫は人の選択を先読みしないため、
お客が通常行動を選ぶと猫だけの発動となる。関心80未満では、最終tickや低体力でも発動できない。

### 特別行動の効果

| 組み合わせ | テンション | 関心 | 猫の体力 | 通常行動・反応 |
|---|---|---|---|---|
| お客だけconnect | −80 | 変化なし | 消費0・回復0 | お客の通常行動を置換。特別受け止め表示のみ |
| 猫だけopen_up | +10 | −80 | 人が選んだ通常行動のコスト／停止回復を適用 | 人の通常行動の関心効果は実行。表示する猫行動はopen_up |
| 両方 | −80の後に+10 | −80 | 消費0・回復0 | 両側とも特別行動 |

猫だけの発動時は、通常交流なら版1の通常反応も内部で計算し、関心倍率と履歴に使用する。
この通常反応によるテンション増減は適用せず、open_upの+10だけを加える。
ログには猫の実行行動と通常効果算出用の反応を別項目で残す。停止・変更なら関心増分は0。

消費は通常効果を加える前に実行する。例えば関心90でopen_upし、通常効果+12なら22となる。
connect自体は飽き履歴を進めず、最後の交流種類と連続回数を保持する。
直前行動はconnectになるため、停止→フェイントの連携を途中のconnectで持ち越さない。
通常反応のないconnect後は、adapt判定用の直前通常反応を「なし」にする。
猫だけopen_upのtickでは、算出した通常反応を次回adapt用に保存する。

## 4. ボーナスと成功条件

| イベント | この交流への資金加算 |
|---|---:|
| connect実行 | +50 |
| open_up実行 | +50 |
| 同じtickで両方実行 | さらに+100 |

同時発動の合計は200。別tickで1回ずつなら合計100となる。
ボーナスは発動を実行したtickに1回だけ加算する。予約成立時・終了時には加算しない。
単独交流の通常獲得分は0とし、今回は特別行動の獲得額だけを表示する。
営業への財布反映は後続とし、この累計を既存会計に重複して足さないよう接続を設計する。

関心100で即成功するルールを廃止し、**両側がこの交流で各1回以上特別行動を実行したら成功**とする。
別tickでも成功できるが、同時発動なら追加資金を得られる。
片側だけでは交流は続き、残り時間・体力の範囲内で再発動も可能。資金と発動回数を全件記録する。
成功時の別の追加料金は設けない。

## 5. 1tickの確定処理順と終了優先順位

1. 終了済みでないこと、人の入力が開始時の有効行動であることを確認する。無効なら完全に無更新。
2. 同じ開始状態から両側の発動を確定する。猫は今回の人の選択や今回の結果を参照しない。
3. 発動側のゲージを80消費し、該当予約を消去する。
4. 通常行動がある場合は、その履歴・関心効果・体力消費または回復・種類変更を処理する。
5. テンション変動を適用する。猫がopen_upなら+10のみ。それ以外は通常交流の反応表を使う。
6. ゲージを0〜100へ制限し、発動回数・ボーナスを加算する。残り時間を1減らす。
7. 終了を次の優先順位で1つだけ決定する：体力0なら`exhausted`、両側発動済みなら`success`、残り時間0なら`timeout`。
8. 継続する場合、更新後100の側に次回予約を設定する。終了なら予約を残さず、未実行で失効した予約／100到達をログに記録する。

最後の有効tickの開始時に予約があれば、そのtickで実行できる。
最終tickの結果で100になっても、追加tickを与えないため発動せず終了する。
体力切れは新しい単独交流の既存優先順位を維持する。発動と消耗終了が同時の場合も、実行済みボーナスは取り消さない。
同じtick内でゲージ到達から再発動する連鎖処理は行わない。予約は次回だけに使う。

## 6. 手計算用のターン例

以下は特記しない限り開始体力100、遊びの好み1、履歴なし、残り時間に余裕がある診断用開始状態。
通常のゲーム開始値をこれらの数値に変更するものではない。

| 開始テンション / 関心 | 入力・猫の判断 | 結果 |
|---|---|---|
| 0 / 0 | direct、猫は通常 | 関心12、テンション12、体力95、ボーナス0 |
| 79 / 0 | connectを入力 | 資格不足でエラー。時間・ゲージ・ログは変化なし |
| 80 / 0 | connect、猫は通常 | テンション0、関心0、体力100、+50。まだ継続 |
| 88 / 88 | direct、猫は任意open_up | 関心20（88−80+12）、テンション98（88+10）、体力95、+50。猫側のみ発動済み |
| 80 / 80 | connect、猫は任意open_up | テンション10、関心0、体力100、+200、成功 |
| 100 / 80 | お客は予約connect、猫は任意open_up | テンション30、関心0、+200、成功。強制＋任意でも同時ボーナス |
| 99 / 70 | direct、猫は通常 | テンション100（+12のうち実増分1）、関心82。次回はお客の予約connectと猫の任意open_upを同時発動可能 |
| 70 / 99 | direct、猫は通常（低体力・最終tickでない） | 関心100、テンション82。次回は猫の予約open_upとお客の任意connectを同時発動可能 |
| 100 / 100 | 両方予約 | 次の有効tickでテンション30、関心20、+200、成功 |

片側だけ先に発動した場合の例：テンション80・関心0でconnectし+50、後のtickで猫がopen_upするとさらに+50で成功。
発動tickが違うので同時ボーナスは付けない。

最終tickの例：テンション99・関心0でdirectを実行すると100／12になるが、時間切れで予約失効、ボーナス0。
一方、最終tick開始時に両方100なら、予約を実行して成功し+200となる。

## 7. 実装範囲と検証

次の実装単位は単独交流core・専用設定・CLI・試遊画面・ログ再生まで。学習と営業会計、動作種類追加は含めない。
試遊画面にはテンション、双方の予約、発動状況、獲得資金、「心をつかむ」ボタンを追加する。
猫の任意発動条件も説明し、プレイヤーが同時発動の機会を判断できるようにする。

新しい設定とログはルール版2として保存し、版1の値やログを暗黙に新版として解釈しない。
実装時には版1を指定して再生できる経路を残し、旧モデルを新版へ転用しない。
ログに両ゲージの前後・実消費・超過切り捨て・人の入力・猫の行動・任意／強制・予約成立／失効・
通常反応・各ボーナス内訳を持たせる。ゲージ以外の通常ルールは既存の処理と共通化する。

数値は専用設定に分離し、有限値・非負ボーナス、0 < 消費量 <= 任意閾値 < 強制閾値 <= ゲージ上限を検証する。
初回の比較では本書の80／100／80を使い、実験による変更は別設定・別レポートに記録する。

検証項目：

- 閾値直前・一致・超過、消費残量、通常反応ごとのテンション増減、下限0。
- 停止・変更でテンションを稼げないこと、特別行動と通常反応の二重加算がないこと。
- 猫の任意発動条件と先読み防止、強制予約中の入力、同時発動の全組み合わせ。
- 最終tick、体力切れと発動の同時成立、予約失効、成功と時間切れの優先順位。
- 資金加算が各イベントで1回だけであること、保存再生、旧版回帰。
- 即発動、同時発動待ち、片側反復、停止連打を通常／低体力条件で比較する。

成功率だけでなく獲得資金・消費体力・使用tick・単独／同時発動数・失効予約数を報告する。
具体例は手計算上の期待値であり、まだ実装やテストで確認した結果ではない。
