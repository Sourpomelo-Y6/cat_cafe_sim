# 猫カフェゲームへのローカルAI導入とUnity移行計画

作成日：2026-10-03

追加相談：制作GUI、コミュニケーション行動の画像、汎用的な手を使った各部屋の自動表示については、[相談記録](ContentToolAndRoomPresentationDiscussion.md)を参照。ユーザーの希望と実装前の提案を分けて記録している。

## 1. 推奨する進め方

**既存ゲームに事前生成した絵と短文を付ける → 任意のローカルLLM演出を追加する → UnityからPythonのゲーム処理を利用する → 必要な処理をC#へ移す**、という順序を推奨する。

最初の完成形は「猫の画像、店内背景、お客さんの短い台詞、猫との交流描写がある2Dの経営ゲーム」とする。3D化、自由入力の長い会話、音声、常時画像生成は後続に回す。既存の経営・育成機能だけでも対象が広いため、初期段階では機能を増やすより、現在の操作に視覚と文章を付ける。

本書は実装前の提案である。AIツールのインストール、生成、Unityプロジェクト作成は今回行っていない。GPU・VRAM・RAM、既存のAI環境、希望する画風、配布先は未確認であり、モデルとUnityの版は導入時に決める。

## 2. 現在のプロジェクトをどう活かすか

作業ルートは `CatCafeSim`、PythonプロジェクトとGitリポジトリはその下の `cat_cafe_sim`。既存の仕様資料は [資料索引](README.md) から参照する。本書は最初に依頼された外側の `CatCafeSim/Docs` に作成し、コミット時にリポジトリ内の `cat_cafe_sim/Docs` にも収録した。今後の版管理対象はリポジトリ内の資料とする。

| 確認した実装 | 活用方法 |
| --- | --- |
| `cat_cafe_sim/cat_cafe_sim/cafe_interaction_gui.py` などのTkinter画面 | 画像・文章を小さく試す。最終的に画面部分をUnityへ置き換える |
| `cat_cafe_sim/cat_cafe_sim/cafe_interaction.py` の `CafeInteractionSession` | 操作とゲーム状態を結ぶ窓口。Unity接続用のアダプター候補 |
| `cat_cafe_sim/cat_cafe_sim/core/` | 営業、複数席、体力、関係、経営、派遣などの既存ルールを維持する |
| `cat_cafe_sim/config/` | 個性、特徴、客、施設などの定義を素材・文章の入力へ対応付ける |
| `cat_cafe_sim/cat_cafe_sim/core/cafe_preferences.py` | 毛色・柄と毛の長さを画像仕様に反映する。ゲーム上の個性・特性とは区別する |
| `cat_cafe_sim/cat_cafe_sim/cafe_cat_events.py`、`relationship_presentation.py` | 保存済み出来事と関係段階を、猫の日記や再会描写の入力にする |
| `cat_cafe_sim/cat_cafe_sim/storage/cafe_saves.py` | 保存・再開を維持する。現行保存版2と旧版1の読み込みがある |
| `cat_cafe_sim/cat_cafe_sim/core/cafe_replay.py`、`tests/`、自動プレイ評価 | Unity化や演出追加によってゲーム結果が変わっていないか比較する |

現在も日本語ログや定型の再会表現がある。「文章を一から作る」より、既存の確定情報に自然な描写を付ける方が安全で実装しやすい。既存のQ学習・接客方策とLLMによる文章生成は別の役割とする。通常の接客は現行どおり自動で進める。

## 3. AIを使う場所とタイミング

| 対象 | 初期の方式 | 後続の拡張 |
| --- | --- | --- |
| 猫の立ち絵・顔アイコン | 開発時に画像生成して採用PNGを保存 | 表情差分、少数のポーズ、加入候補の追加素材 |
| 店内背景・派遣先・客の肖像 | 共通画風で事前生成 | 増設段階や季節の差分 |
| 紹介文・再会・交流・派遣結果 | LLMで候補を事前生成し、人が確認してJSONに保存 | 確定イベント発生時にローカルLLMで短文を生成 |
| 日次まとめ・猫の日記 | 既存結果から定型文を表示 | 当日の確定履歴を要約する |
| 自由会話 | 初期対象外 | 客との会話から試す。選択肢式を先行させる |

猫は基本的に「鳴き声・仕草・地の文」で表現する。人間のように話す猫にする場合は世界観の選択が必要。お客さんには短い台詞を付ける。例えば実際に満足退店した客にだけ「今日はゆっくり過ごせました」と付け、休養中の猫には「窓辺で丸くなっています」と描写する。

**ゲーム処理が先に結果を確定し、AIはその結果の表現だけを作る。** 資金、報酬、好感度、病気、加入、イベントの発生条件をLLMに決めさせない。会話に選択肢を導入するときも、合法な操作IDはゲーム側が用意し、LLMはラベルの候補だけを作る。

## 4. ローカル画像生成の制作工程

### ツールとモデル

第一候補はComfyUI。ワークフローを保存し、同じ制作工程を再利用できる構成にする。モデルは最初から固定せず、同じ猫・背景の課題で候補を比較する。日本語の説明から実際の画像プロンプトへの変換も必要に応じて制作ツール側で行う。

ComfyUIのローカルサーバーには `/prompt`、`/history/{prompt_id}`、`/view`、`/ws` などの経路がある。自動化する場合はAPI用ワークフローを渡してジョブIDを受け取り、完了と出力を確認して採用候補を保存する。GUI用のワークフローJSONをそのまま送る前提にしない。[公式サーバー経路](https://docs.comfy.org/development/comfyui-server/comms_routes)、[進行通知](https://docs.comfy.org/development/comfyui-server/comms_messages)

### 最初の素材セット

1. 猫1匹の基準画像を作り、毛色・柄・毛の長さ・目・輪郭・画風を決める。
2. 同じ猫の通常・喜び・疲れの3差分を作る。初期の提案値は512×512のPNG。
3. 同じ画風で店内背景を1枚作る。初期の提案値は1280×720。
4. 表情差分の同一性を確認し、必要に応じて参照画像、部分修正、手直しを使う。同じseedだけで同一個体を保証できるとは考えない。
5. 透過が必要な立ち絵は背景除去と縁の修正を行い、実際のGUI背景上で確認する。背景画像は不透明とする。
6. 猫を数匹へ増やし、必要になった段階で客や派遣先を追加する。

画像にはボタン名や台詞を描かせず、文字はGUIで重ねる。小さなアイコンは縮小して見分けられるか確認する。まず静止画と切り替えで成立させ、歩行アニメーションや多方向スプライトはUnity側の画面設計が固まってから作る。

採用素材には `asset_id`、対象の猫ID、表情、ファイル名、生成モデル・モデルの識別情報、seed、プロンプト、ワークフロー版、参照画像、利用条件を記録する。採用PNGそのものを保存し、再生成で完全再現できることを前提にしない。モデル重みや大量の不採用画像は通常のソース管理へ入れない。

## 5. ローカルLLMによる文章生成

### ツールと入力

第一候補はOllamaのローカルAPI。日本語の自然さ、短文の安定性、実機速度を比べてモデルを決める。モデルサイズだけで選ばず、同じ30件程度の確定イベントで比較する。

`POST /api/chat` にモデル名・メッセージを渡せる。初期実装は `stream: false` とし、`format` にJSON Schemaを指定して扱いやすい構造を要求する。ただし構造が正しくても内容の事実性は別途検証する。[公式API](https://docs.ollama.com/api/chat)、[構造化出力](https://docs.ollama.com/capabilities/structured-outputs)

ゲーム全体のセーブを送らず、公開してよい確定事実だけを抽出する。隠れた好み、内部評価値、未発生のイベントは渡さない。入力例と出力例は以下の**新規設計案**であり、現行のイベント形式ではない。

```json
{
  "event_id": "session-a:day-3:interaction-12:finished",
  "event_type": "customer_departed_satisfied",
  "speaker_id": "customer-demo",
  "cat": {"id": "cat-demo", "name": "ミケ", "features": ["calico", "short_hair"]},
  "public_facts": ["客は満足して退店した", "ミケと遊んだ"],
  "style_version": "ja-cozy-v1"
}
```

```json
{
  "speaker_id": "customer-demo",
  "text": "ミケと遊べて楽しかったです。また来ますね。",
  "expression": "happy"
}
```

初期仕様は1～2文・最大100文字程度。出力スキーマは必須キー、余分なキー禁止、文字数上限、話者ID、表情の列挙値を定義する。名前・出来事・金額を勝手に追加しないよう指示する。金額や重要な結果はゲーム側の固定表示に任せ、生成文では説明を補う。

### 停止・矛盾・再開への対応

- AI停止、タイムアウト、不正JSON、話者不一致、許可していない表情は、既存の定型文へ戻す。
- 実行は別の作業スレッドまたはプロセスに分ける。Tkinterの画面更新はメインスレッドで `after()` を使う。Unityも非同期で待ち、操作を止めない。
- 回答にはイベントIDと画面状態の版を対応付ける。画面を閉じた後やロード後に届いた古い回答は破棄する。
- `event_id + 公開事実のハッシュ + モデル識別情報 + プロンプト版 + スキーマ版` をキャッシュキーにする。同じ結果を再表示しても再生成しない。
- 採用した文章は保存し、再開時はその文章を表示する。LLM用の乱数や生成順序をゲームの乱数系列から分離する。
- 長い会話履歴を延々と投入せず、短い公開履歴を上限付きで渡す。事前生成なら人が確認してから採用する。実行時生成には完全な意味検証が難しいため、対象イベントを狭くする。

## 6. データと実装の境界

以下は追加先の案。すべて内側のPythonプロジェクト `cat_cafe_sim/` からの相対パスで、まだ存在することを意味しない。

```text
content/
  assets_manifest.json          # 猫ID・表情と画像の対応
  text_templates.ja.json        # AIなしでも使える文章
  approved_dialogue.ja.json     # 確認済みの生成文章
  portraits/ backgrounds/      # 採用した素材
tools/content_generation/      # 制作用の生成・確認・書き出しツール
cat_cafe_sim/presentation/      # 公開情報の抽出、表示データへの変換
cat_cafe_sim/ai/                # Ollama接続、検証、キャッシュ
cat_cafe_sim/bridge/            # Unity接続用のローカル窓口
```

素材IDとゲーム内IDを対応付け、表示名をファイル名や識別キーに使わない。画像欠落時には共通の代替画像を表示する。台詞のspeakerと表情も同じIDで結ぶ。制作メタデータと配布用データは別に書き出す。

現行 `cafe_saves.py` は保存キー集合を厳密に検証するため、既存セーブへ独断で画像や台詞のキーを追加しない。初期は別ファイルに演出キャッシュを置き、セッションIDとゲーム状態の識別情報で対応付ける。キャッシュが欠けてもゲームをロードできる設計にする。後で統合する場合は保存版を上げ、旧版からの移行・不正データ検証を実装する。

ゲームの操作ログと会計結果は今の仕組みを正とし、生成文は別の表示履歴とする。リプレイは保存した文章を利用し、LLMへ再問い合わせしない。

## 7. Unity移行の選択肢

| 方式 | 利点 | 課題 | 推奨段階 |
| --- | --- | --- | --- |
| Unity画面＋Pythonのローカルサーバー | 既存ロジックを再利用して早く遊べる | Pythonプロセスの起動・終了・配布が必要 | 最初のUnity版 |
| Unity画面＋C#のゲーム処理 | 単独ビルドを作りやすい | 数多くのルール・保存・乱数を移植する必要 | 将来の完成版 |

最初はWindowsデスクトップ向け2Dを仮の対象にする。PythonをUnity内へ直接埋め込む構成は初期案にしない。WebGLやモバイルではローカルPython・AIの扱いが変わるため、別途設計する。

### UnityからPythonへ接続する最小版

Unityは猫・客の一覧、出勤と休養、席への割り当て、営業進行、閉店結果、保存・再開を表示する。Python側は既存Sessionを操作する窓口を追加する。UI Toolkitは一覧・パネル中心のUI候補で、Spriteを使う店内表示と組み合わせる。使用するUnity版を固定した後、必要なUI機能を小さな画面で検証する。[公式UI Toolkit資料](https://docs.unity.com/en-us/engine/6000.6/manual/uitoolkits/uielements)

接続APIの設計案は `GET /health`、`GET /state`、`POST /commands`。表示用JSONはUnityが必要とする情報だけを含め、内部のPythonオブジェクトを直接送らない。コマンドには `request_id` と期待する状態版を付け、サーバーが順番に処理する。同じ操作の再送で営業や会計が二重に進まないようにする。通信が途切れたら状態を再取得し、確定していない操作を推測で進めない。

Unityは `UnityWebRequest` などで通信できる。[公式通信API](https://docs.unity.com/en-us/engine/6000.3/script-reference/unityengine/networking/unitywebrequest)

初期はPythonを手動起動して接続し、動作を確認する。その後Unityから起動・準備完了確認・終了を管理する。接続先はループバックに限定し、ゲーム所有プロセスだけを終了する。Pythonが止まっても状態を壊さず、再接続や保存からの再開へ誘導する。AIのサーバーとは別の役割・設定にする。

### C#へ移す場合

単独ビルドで遊べることが目標なら、最終的にルールをC#へ移す。ただし全機能を一度に書き直さず、状態モデルと設定読込 → 最小の営業 → 閉店会計 → 保存 → 育成・客・派遣・目標の順に進める。移植途中の同じ状態をPythonとC#の両方で更新しない。

Pythonで固定初期状態と操作列の基準データを作り、C#で日付、資金、猫の体力・ストレス、関係、報酬、終了状態を比較する。seedを合わせるだけではPythonとC#の乱数が一致しないため、共通乱数方式を定義するか、最初は記録した乱数値を入力して比較する。浮動小数点・丸め・処理順序も対象にする。

旧Pythonセーブを読みたい場合は、版付きの変換器を用意する。現行のセーブをUnityの保存形式としてそのまま解釈できるとは考えない。現行の自動プレイ方策とQ学習方策も、通常ゲームに必要な範囲を確認してから移植対象にする。

## 8. 段階ごとの作業と完了条件

| 段階 | 作業 | 完了条件 |
| --- | --- | --- |
| 0：前提確認 | GPU・VRAM・RAM・空き容量、画風、対象端末、AI環境を記録。現行の起動と保存を確認 | 比較用の初期セーブ・操作列がある |
| 1：制作実験 | 猫1匹の3差分、背景1枚、紹介・交流・再会の短文を制作 | 見た目が統一され、事実と一致する文章を採用できる |
| 2：現行GUIに追加 | マニフェスト、定型文、画像枠、確認済み文章の表示 | AI停止状態でも開始・営業・閉店・保存再開ができる |
| 3：任意のLLM演出 | 交流終了や閉店など少数のイベントだけ非同期生成 | タイムアウト・不正出力・再開・古い応答でも操作を続けられる |
| 4：Unity最小版 | Python接続、猫・席・営業・閉店・保存を実装 | 猫数匹と最小店舗で一日の流れをUnityから遊べる |
| 5：Unity機能拡張 | 目標、派遣、施設、客、詳細画面を順に追加 | 対応する操作列でPython基準の結果と一致する |
| 6：配布形態を完成 | Python同梱版の整備、またはC#移植。採用素材と文章を同梱 | 開発環境のない対象PCでAIなしでも遊べる |

最初の実装単位は **「猫詳細画面に猫1匹の画像と確認済み紹介文を表示する」** に絞る。次に交流後の描写を付ける。この段階で操作の分かりやすさと見た目を確認してから、猫数や生成箇所を増やす。各段階の所要時間は実機生成速度と必要素材数を測ってから見積もる。

## 9. 実機評価と配布

画像モデルとLLMを同時にGPUへ常駐させるとメモリが競合し得るため、初期は画像を制作時に生成し、実行時は必要なLLMだけを使う。モデルの量子化、画像サイズ、文脈長で必要メモリは変わる。特定のVRAM容量だけを根拠に動作保証しない。

測る項目は、画像1枚の生成時間、猫の差分の一致率、LLM初回と継続時の応答時間、最大メモリ、JSON不正率、事実矛盾、採用率。初期の待ち時間予算は文章5秒程度を仮置きし、超えたら定型文に戻す。ゲームの進行を生成完了待ちにしない。

配布方式は「採用済み素材・文章を同梱したAI不要モード」を基本とし、「自分のPCのローカルLLMを接続する追加モード」を任意にする。モデル重みの同梱はサイズと利用条件を確認して別に判断する。モデル本体・LoRA・参照画像・フォントの条件と出典を記録し、利用条件に沿った素材だけを配布する。

## 10. 検証項目

- 同じ初期状態・操作列で、演出ON/OFFのゲーム結果が一致する。
- 生成待ち中もスクロール・画面移動・保存などが動く。
- 猫の毛色と長さが既存特徴と一致し、ID取り違えがない。
- AI停止、画像欠落、不正JSON、長すぎる文章、古い応答で代替表示へ戻れる。
- 保存再開・リプレイで同じ採用文章を表示し、会計と関係更新を二重に実行しない。
- Unicodeの猫名、文章折り返し、日本語フォント、異なる画面サイズを確認する。
- Unity通信再送とPython異常終了でも状態の更新は一度だけになる。
- C#移植部分はルールごとの基準データと一致し、未移植機能を遊べると表示しない。

既存の `python -m unittest discover -s tests` は内側の `cat_cafe_sim` を作業ディレクトリにして実行する。GUIテストの設定は既存READMEを参照し、Windows実機では追加した画面も目視確認する。本書作成時にはゲームコードの変更・テスト実行を行っていない。

## 11. 次の作業で決めること

1. イラスト調・ドット絵調などの画風と、猫の表現を現実寄りにするか。
2. 実機のGPU・VRAM・RAMと、すでに使っているComfyUI・Ollama等の有無。
3. 初期Unity版をWindows限定とするか、他端末も対象とするか。
4. 事前生成だけで始めるか、短文の実行時生成まで含めるか。

未確定の間は「2Dの静止画、猫は仕草と地の文、Windows向け、画像と文章は事前生成」を仮案として進める。GPU性能が不足しても、制作済みコンテンツの表示とUnity移行は進められる。
