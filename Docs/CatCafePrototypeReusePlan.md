# 猫カフェゲームへのプロトタイプ活用・引き継ぎ方針

記録日：2026-09-05

## 目的と位置づけ

参照元 `/home/hi-wa/learning` で試行してきた会話強化学習プロトタイプの成果を、[猫カフェゲーム実装資料](CatCafeSimulation_ImplementationGuide.md)のゲーム開発に利用する。猫カフェの作業場は `/home/hi-wa/learning/cat_cafe_sim` とし、参照元には会話の実験結果と参照実装を残す。文中の会話用ソースファイルは参照元からの相対パスである。

ドキュメント移動時点の参照元コミットは `01ad458`（Add playable conversation GUI）。新作業場は現リポジトリ内のサブフォルダとして用意したもので、独立したGitリポジトリの初期化やコミットはまだ行っていない。

猫カフェへの活用は相性がよいと考える。特に「非公開の好みを反応から推測する」「同じ行動を続ける効果と飽きを分ける」「満足と消耗の釣り合いを学習する」「固定方策・ランダム方策と比較する」という既存の実験テーマが、猫と客の接客に対応する。

ただし、既存の学習済み会話方策が猫の接客や店舗経営でも通用することを示す結果はない。再利用の中心は設計、汎用部分のコード、検証手法であり、猫カフェ用の状態遷移と学習モデルは新しく作る。本書は移行案であり、実装資料中の暫定値を製品仕様として確定するものではない。

## 役割の対応と違い

| 会話プロトタイプ | 猫カフェへの活用 | 注意点 |
|---|---|---|
| 話し手の行動選択 | 猫AIによる交流パターンと速度の選択 | 観測、行動数、報酬の意味が変わるため再学習する |
| 聞き手の反応と非公開の興味 | 客の好みと接客への反応 | 初期の客はルール処理とし、独立した学習エージェントにする必要はない |
| 話題鮮度と行動履歴 | 接客行動への飽き、継続効果、切り替え効果 | ジャンル6種をそのまま接客行動6種へ置換すると、速度変更だけで飽きを回避する抜け道になり得る |
| 好感度、満足度、疲労の分離 | 来店中の満足、常連関係、猫の体力・気力・日跨ぎ疲労 | 一つの値にまとめず、各値の持続期間を定義する |
| 複数会話にわたる記憶 | 顧客履歴、猫との面識、お気に入り関係 | 20ターン×10会話という長さは移植せず、営業日と来店単位で設計する |
| 人間とAIから環境を操作 | 人間店長と代理店長Botが同じコマンドを使う | プレイヤーは通常、猫の毎tickの交流行動ではなく店舗運営を操作する |

既存V12のプレイ相手である `FixedGenreListener` は、学習済みモデルではなくルールベースの非学習方策である。この「片方を固定して学習対象を検証する」構成が、猫方策を固定して店長AIを評価する進め方の参考になる。猫と店長は接客と経営という異なる時間幅の意思決定を担うため、話し手・聞き手を名前だけ置き換えた構成にはしない。

## 再利用するコードと新規実装

| 参照元 | 再利用候補 | 新フォルダでの扱い |
|---|---|---|
| `conversation_q_learning.py` | Q表の更新、探索、保存・読込 | Phase 2で必要な部分を抽出し、接客用状態と行動に合わせる |
| `conversation_dqn.py` | ネットワーク、経験再生、モデル保存 | Q表が適さなくなった場合の参考。初期からDQNを必須にしない |
| `conversation_dqn_v6_fixed_listener.py` | 固定方策を基準にした比較 | 猫用・店長用の固定方策を新設する。会話の反応規則自体は移植しない |
| `conversation_env_v6.py`、`conversation_env_v7.py` | 好み・鮮度・履歴の分離、長期状態の保持 | 必要な考え方を `SimulationCore` に組み直す |
| V12の評価スクリプトと各種分析 | 複数seed、未知条件、学習前後の比較、CSVと図 | 指標を利益、満足退店、消耗、病気、離脱などへ置き換える |
| `play_conversation_gui.py`、`play_conversation_cli.py` | UIと進行処理の分離、操作ログの保存 | 店長用コマンドと店舗画面に再設計する |

`ConversationEnvV12`までの版ごとの継承関係、旧実験スクリプト一式、会話用のモデル重みやQ表は、新しい実行環境の依存にしない。新プロジェクトからこのフォルダを直接importせず、採用した小さな部品だけをコピー・整理し、参照元のファイルとコミットを記録する。仮想環境、生成済みoutputs、GUI依存も一括コピーしない。

猫・客・席・財布・営業時間、待機列、会計、健康、シフト、設備、店長コマンドは新規実装する。学習やUIから独立した `SimulationCore` を作り、実装資料の `CatInteractionEnv` と `CafeManagementEnv` で利用する。

コードの抽出時には、次の点を確認する。

- 現行 `DQNAgent` は行動選択時にマスクを使う一方、次状態の最大Q値計算にはマスクを適用していない。移植する場合は、学習時にも無効行動を候補から除外する設計にする。
- 終了を単一の `done` にまとめた既存処理は、猫カフェ仕様の `terminated` と `truncated` の意味に合わせて見直す。
- 方策だけをimportしても描画や学習依存を読み込む既存構成は整理し、UIなしの営業シミュレーターを軽く実行できるようにする。
- JSONの状態履歴を保存できることと、同じ結果を再生できることは別である。設定・方策版・seed・コマンド列を保存して再実行結果を照合する。

## 既存実験から持ち込む検証上の教訓

### 行動の偏りと報酬

特定行動への集中率を下げること自体を目標にしない。客の好み、設備、猫の状態によって同じ行動が合理的になる場面は許容する。問題とするのは、相手や状態に関係なく単純連打・固定ループだけで勝てる場合や、選択肢が実質的に機能しない場合である。

会話実験では通常開始の好成績だけでは深い負の状態からの回復を保証できなかった。猫カフェでも、通常営業の平均だけでなく、低気力、混雑、相性の悪い客、病欠、資金不足などを段階に応じて評価する。状態変化の速度や報酬係数を変えたら、既存方策の転用評価と再学習後の評価を分ける。

既存の好感度半減、負の好感度、固定値30への修復は会話用に調整したルールである。猫カフェの満足や常連度へ数値をそのまま移さず、1接客・1営業日・複数日の進行に合う尺度を決める。

### 特別成功の頻度

会話GUIの試遊では「心が通じ合う」が出しやすいという感想があった。猫カフェの「満足達成と体力0が同時に起きる特別成功」でも、成功回数だけでなく、成立までの行動、気力消費、その後の接客不能や疲労を記録する。

二者のゲージ同期と、満足達成・体力切れの同時イベントは別の仕組みである。既存の80以上で任意発動・100で強制発動という規則は持ち込まない。特別成功の頻発や最大化を自動的な採用条件とせず、狙う楽しさと猫の消耗を併せて評価する。

### 人間の操作負担

CLI試遊の負担は、難易度や会話数だけでなく「毎回キーとEnterを入力する操作」にあった。猫カフェも自動検証用のUIなし実行と、人間が判断を試す画面の両方を用意する。

最小営業の検証後、人間の試遊ではボタンによる割り当て、シフト指定、時間の一時停止・進行を候補とする。猫の各行動を人間が毎tick承認する操作にはしない。UI方式は未確定であり、Tkinterは参照例として扱う。

## 別フォルダでの着手順序

1. 実装資料と本書を新フォルダへ引き継ぎ、参照する現フォルダのコミットIDを記録する。
2. Phase 1として猫1匹・席1つ・固定客・固定方策で1営業日を完走させる。満足、体力、気力、会計、閉店の処理順を実装する。
3. 満足達成と体力0、気力が回復コストと同値／未満、閉店との同時発生、二重会計、同seed・同操作の再現を検証する。
4. Phase 2で接客用の観測と状態数を絞り、Q学習を追加する。未使用条件でRandom・固定方策と比較し、モデル保存・再読込も確認する。
5. 人間が確認する画面を必要に応じて追加し、接客の見え方と店長操作を試す。
6. Phase 3で複数猫、常連、設備、曜日、休養、病気、交代を加える。
7. Phase 4で猫方策を固定した店長学習と複数目的Botによるバランス検証を行う。

最初の完了条件は「会話モデルを動かすこと」ではなく、「猫カフェ仕様の1営業日が、境界条件を含めて再現可能に動き、会計とイベントを説明できること」とする。猫の成長・加入方法、最終UIなどの未確定事項は実装資料に従って管理する。
