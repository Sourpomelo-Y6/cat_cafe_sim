# 猫カフェシミュレーションゲーム：Codex向け実装資料

作成日：2026-09-05  
参照会話：猫カフェシミュレーションゲーム案  
目的：ゲーム企画、猫の強化学習、プレイヤー代理AIによるバランス検証を、段階的に実装できる仕様として整理する。

## 1. 資料の位置づけ

既存の会話強化学習プロトタイプから再利用する設計・コードと、別作業フォルダでの着手方針は、[プロトタイプ活用・引き継ぎ方針](CatCafePrototypeReusePlan.md)を参照する。

本資料は、提示された会話内容を基にした引き継ぎ資料である。「原案」はユーザーが提示した内容、「提案」は会話内の助言または実装のために本資料で補った暫定仕様を指す。数値、計算式、学習方式、Phase分割は確定仕様ではない。実装時は設定ファイルで変更できるようにする。

まず完成させるのは、UIなしで再現可能に営業を実行できるシミュレーターである。猫AIはゲーム内の行動選択を担い、店長AIは開発時に人間の操作を代行する。店長AIの成績はバランスを判断する材料であり、人間が遊んで楽しいことの証明にはならない。

## 現在の開発方針（2026-09-17）

ユーザー方針として、**細かいバランス調整は後回しにし、ゲーム全体の流れを固めることを優先する。**
全体の流れがまだ確定していないため、個別の数値を詰めることを次の作業にはしない。

- 営業前の準備、営業中の判断、営業後の結果確認、翌日以降の経営・成長がどうつながるかを先に整理する。
- 疲労回復量20・30・40の比較、発症率・疲労係数・収益などの細かな調整や、そのための追加の長期比較は保留する。
- 現行の数値は暫定値として使う。実装済みの休養提案機能、検証コード、過去の測定結果は残し、全体の流れが固まった後の調整材料にする。
- 全体を通して遊べる流れと、プレイヤーが何を判断し何を目指すかを整理した後に、必要な調整項目と検証条件を改めて決める。

過去の検証資料にある「次に回復量を比較する」などの記述は将来の候補として扱い、直近の開発順序はこの方針を優先する。

2026-09-20に[ゲーム全体の流れと実装順](HumanToCatGameFlowPlan.md)を整理した。通常営業の実装済み・未実装・未決定事項と、最初の通しプレイを作るための提案はそちらを参照する。本資料の原案・Phase順序は当初計画として残し、新しい提案を確定仕様と混同しない。
進行不能や保存・表示の不具合など、全体の流れを確認するために必要な修正は通常どおり対応する。

## 2. ゲームの狙いと基本ループ

猫と客の相性を考え、猫の健康を保ちながら客を満足させ、収益で店を育てる経営シミュレーションとする。実際の猫カフェの料金体系には合わせない。

| タイミング | プレイヤー／店長AIの判断 | シミュレーターの処理 |
|---|---|---|
| 営業前 | 曜日と常連情報を確認、猫の出勤・休養を決定、席設備を購入・変更 | 体調確認、当日の来店予定生成、営業席の確定 |
| 営業中 | 来客への席・猫の割り当て、必要に応じて猫を交代 | 猫AIの行動、満足・体力・気力更新、時間経過、退店と会計 |
| 営業後 | 売上・不満・疲労を確認、翌日以降を計画 | 費用精算、疲労・病気・常連情報更新、翌日へ移行 |

短期の判断は「この客をどの猫で満足させるか」、中期は「今日の勤務量をどう配分するか」、長期は「曜日ごとの常連に合わせて猫と設備をどう育てるか」とする。

## 3. 猫の体力・気力・疲労

### 3.1 原案

- 行動で体力を消費する。
- 体力が0になると気力を消費して体力を最大まで回復する。
- 気力がなくなると客が不満を持って帰る。
- 休養不足で疲労が蓄積し、病気になる。

### 3.2 データと暫定ルール

| 値 | 役割 | 暫定更新方針 |
|---|---|---|
| `stamina` / `max_stamina` | 接客中の短期リソース | 行動ごとに減少。範囲は0〜最大値 |
| `spirit` / `max_spirit` | その日の接客継続力 | 体力回復時に一定量消費 |
| `fatigue` | 日をまたぐ無理の蓄積 | 勤務・気力消費で増加し、休養で減少 |
| `health_status` | 健康／病気 | 病気の猫はシフトに入れられない |
| `recovery_days_remaining` | 病気の残り日数 | 営業後に減少、0で復帰 |

提案として、体力上限100、気力上限100、体力回復コスト30などを初期値にする。ただし、気力の端数と0到達時の処理を曖昧にしない。

暫定仕様は「回復コスト以上の気力があれば消費して体力を全回復する。ただし消費後の気力が0なら接客不能。コスト未満なら回復せず接客不能」とする。後者は残量を記録したまま `cannot_continue` として扱う。0到達まで接客を許す別案と比較できるように、ルールを設定化する。

営業開始時に健康な猫の体力・気力を最大まで戻す案を採用する。疲労は持ち越す。疲労による能力低下はPhase 1では入れず、後で追加する。営業中の「休む」は少量の体力回復だけとし、気力と長期疲労の回復は行わない。

営業後の疲労は、例えば次式で更新する。

```text
出勤猫：翌日疲労 = clamp(疲労 + 接客tick数×勤務係数 + 気力消費量×負荷係数, 0, 上限)
休養猫：翌日疲労 = max(0, 疲労 - 休養回復量)
病気確率 = clamp(max(0, 翌日疲労 - 安全閾値)×病気係数, 0, 最大確率)
```

病気判定は1日1回。病気中の猫には重複発症判定を行わない。係数と回復日数は設定値とする。

### 3.3 同時イベントの優先順位

1. 行動開始時の条件を確認し、満足度変化と体力消費を算出する。
2. 満足度と体力を更新する。体力は0で下限処理する。
3. 満足目標到達なら接客成功として退店する。体力も0なら特別ボーナスを1回だけ付ける。
4. 満足未達で体力0なら、気力による回復と接客継続可否を判定する。
5. 接客不能なら不満退店する。
6. 閉店なら残る客を通常の閉店退店にする。

成功退店時には不要な体力全回復を行わない。次の接客開始前に体力0なら回復判定を行う。成功と失敗の報酬・会計を同じ客に二重計上しない。

原案の「体力切れと満足上昇が重なるボーナス」は、提案として「同じ行動で体力0と満足目標到達が重なった場合」に限定する。任意の満足上昇を対象にすると、体力切れの繰り返しが目的になる恐れがあるため、元の条件も比較対象として保存する。

## 4. 客・会計・常連

| 項目 | 内容 |
|---|---|
| 満足 | 来店ごとに初期化する進捗。目標到達で成功退店 |
| 今回来店の不満 | 待ち時間、接客不能などで発生する不満 |
| 累積不満 | 顧客ごとに持ち越す値。閾値到達で再来店しない |
| 常連度 | 良好な来店の積み重ね。累積不満と別管理する提案 |
| 来店曜日 | 顧客ごとの決まった曜日。曜日外来店や欠席確率は後で追加可能 |
| お気に入り猫 | 顧客と猫の関係。割り当て時の満足補正に使う |
| 行動の好み | 行動種類、速度、継続・切り替えへの好み |
| 来店履歴 | 初来店、訪問回数、前回担当猫、満足退店回数 |

「今回来店の最初の行動」「その顧客の初来店」「その猫との初対面」は別のフラグとして持つ。

会計の原案は、滞在時間に応じた料金と、満足退店時の追加料金である。

```text
請求額 = 着席後の滞在tick数 × 時間単価
       + 満足退店時のボーナス × 特別成功倍率
```

不満退店と閉店退店にも基本料金を適用する暫定仕様とし、返金は初期実装に含めない。待ち行列での時間には課金しない。閉店だけを理由に累積不満を増やさない。不満退店時の加算量、満足時の累積不満減少、常連判定閾値は設定化する。

課金目的で客を長時間滞在させる戦術を必ず検証する。最大滞在時間や満足不足による不満は対策候補であり、初めから原案の確定ルールとして扱わない。

## 5. 席設備・曜日・猫シフト

原案は「猫の数だけ席を作れる」「資金で席をカスタマイズできる」。暫定的に、設置席数の上限は所属猫数、同時接客数の上限は出勤中かつ接客可能な猫数とする。休養猫がいても席自体は消えず、その日は一部を営業対象外にする。

各猫は同時に1席のみ、各席は客1人・担当猫1匹まで。猫の交代は原案への追加提案とし、気力切れで退店が確定する前に行う。交代しても客の満足と滞在時間は引き継ぐ。交代に時間または費用を設定し、無制限の交代で得をするか検証する。

| 設備 | 効果候補（未確定） | 比較する点 |
|---|---|---|
| キャットタワー | 遊び系行動の満足補正 | 消費体力との釣り合い |
| 猫鍋 | 特定の客・猫との相性補正 | 猫鍋だけが最適にならないか |
| 猫用クッション | 休む行動の体力回復補正 | 滞在引き延ばしを助長しないか |
| ソファー | なでなで系の満足補正 | 価格に対して効果が強すぎないか |

初期は1席1設備とする。購入価格、維持費、補正対象、補正倍率はデータ定義へ分離する。

1週間は7日とし、営業前に今日と今後の曜日別常連情報を確認できる。人気猫の出勤を常連の曜日に合わせる一方、連勤を避ける判断を作る。来店予定の完全な時刻や非公開の好みは人間にもAIにも見せない。新しい猫の加入方法は原案では未定なので、初期は固定頭数とする。

## 6. 猫AI：状態・行動・報酬

### 6.1 役割と観測

猫AIは、接客中の「なでなで」「ねこじゃらし」などの交流パターンを選ぶ。表現上は客と猫のやり取りだが、実装上の行動選択主体を猫AIに統一する。席の購入やシフトは選ばない。

観測候補は、客タイプ、満足度の段階、猫の体力・気力、直前行動と速度、同じ行動の連続回数、今回最初の行動か、初来店か、猫との面識、お気に入り関係、席設備、閉店までの残り時間とする。好みが非公開の場合は、推定値や過去反応のみを入力する。

継続効果やコンボが過去の行動に依存するなら、その計算に必要な履歴を観測に含める。Phase 2のQ学習では項目を絞り、値を少数の区間に離散化する。全候補の直積をそのままQ表にすると状態数が大きくなりすぎる。

### 6.2 行動

```text
0: ねこじゃらし・ゆっくり
1: ねこじゃらし・普通
2: ねこじゃらし・素早く
3: なでなで・ゆっくり
4: なでなで・普通
5: なでなで・素早く
6: 休む
```

最初は各行動1tickとし、速度は満足効果と体力消費を変える。速度と力加減を両方実装すると組み合わせが増えるため、原案の強弱はまず速度の3段階で表現する。

満足変化は「基本効果×客の好み×設備相性×継続補正＋切り替えボーナス」などで計算する。強い行動の連打だけが有利にならないよう、同一行動への飽きと適切な切り替えを導入する。ただし、切り替えるだけの固定ループも検証する。

### 6.3 報酬案

```text
r_satisfaction × 実際の満足増分
+r_success      × 満足退店イベント
+r_perfect      × 特別成功イベント
-r_stamina      × 体力消費量
-r_spirit       × 気力消費量
-r_discontent   × 不満増分
-r_failure      × 不満退店イベント
-r_time         × 経過tick数
```

各係数は仮値で、項目別の寄与をログに残す。満足を下げてから上げ直すことで得をしないよう、満足増分は符号付きで扱う。時間罰は「休み続ける」戦術を確認した上で調整し、猫の消耗を過剰に促さないようにする。

単一接客の学習だけでは翌日の疲労や常連離脱を直接最適化できない。猫AIは接客品質を担当し、長期的な健康・利益は店長AIと営業ルールで扱う。猫ごとの個性は行動補正、探索率、報酬傾向などで作る案があるが、評価中は学習・探索設定を固定する。

## 7. 店長AI（プレイヤー代理）

店長AIは、シフト、来客の席と猫の割り当て、猫の交代、設備購入、営業開始・終了を操作する。人間と同じコマンドを使うため、店長AIを外せば人間が遊べる。

観測は資金、曜日、残り営業時間、猫の体力・気力・疲労・病気、席設備、待機客と着席客、公開された常連履歴とする。内部の乱数、将来の確定来店列、非公開の好みは渡さない。

学習開始時は猫方策を固定する。店長と猫を同時に学習させると、成績変化の原因を区別しにくい。後段で「猫を固定して店長を学習→店長を固定して猫を学習」の交互更新を試し、評価時は両方を固定する。

### 7.1 複数目的Bot

| Bot | 主目的 | 併せて見る副作用 |
|---|---|---|
| 利益Bot | 費用を引いた利益・期末資金 | 猫の酷使、顧客切り捨て、滞在引き延ばし |
| 満足度Bot | 満足達成人数・満足率 | 簡単な客だけ選ぶ、利益不足 |
| 猫好き／健康Bot | 疲労・病気の抑制 | 休業が最適になる |
| 常連Bot | 常連維持・離脱抑制 | 新規客を無視する |
| 拡張Bot | 使用可能席・設備価値の増加 | 無意味な購入、資金枯渇 |
| 総合Bot | 利益・満足・健康・常連の加重和 | 重みの偏りで他目的が消える |

健康Botなどの純粋な目的は極端な戦術の検出に使う。通常営業の比較では最低来客対応率などの共通条件を別途課し、純粋目的の実験と区別する。平均満足だけでなく未対応客も記録する。

店長報酬では日次利益と期末資金を無条件に足して二重評価しない。初期資金との差、設備購入、維持費、治療費などの扱いを定義する。報酬の尺度を正規化し、金額の大きさだけで総合Botの目的が決まらないようにする。

## 8. AIプレイヤーによる自動バランス検証

### 8.1 上手さを変えるBot

| 水準 | 実装案 |
|---|---|
| Random | 実行可能な行動からランダム選択。乱数を固定できる |
| 初心者 | 目先の空席・元気な猫を優先。翌日以降を考えない固定ルール |
| 中級 | お気に入り・設備相性・疲労閾値を考慮する固定ルール |
| 上級 | 曜日別需要を予測し、数日分の休養や投資回収を考える方策 |
| 最適化 | 十分な学習または探索で高得点を狙う方策。最適性の証明はしない |

目的と上手さは別軸とする。最初は総合目的で水準を比較し、その後に目的別Botへ広げる。学習途中のモデルを初心者・中級者と呼ぶ場合も、未使用シナリオで実力を測定する。名称だけで人間相当と判断しない。

### 8.2 評価手順

1. 設定、シミュレーター版、猫方策、店長方策、乱数seedを固定する。
2. 学習用、調整用、最終評価用の来店条件・seedを分離する。
3. 例として100日営業を1試行とし、複数seedで各Botを実行する。
4. 同じ来店シナリオ・初期条件でBot間と設定変更前後を比較する。
5. 平均、中央値、ばらつき、下位成績、破綻率を集計する。
6. 極端な成績の試行を行動ログから再生し、原因を確認する。
7. 設定を変えたら、既存方策での回帰評価と再学習後の評価を分けて行う。

試作時の目安は調整用20seed、最終比較100seed。これは品質保証値ではなく、速度と成績のばらつきに応じて見直す。学習seedも複数使い、学習運による差を確認する。

集計項目は利益、期末資金、満足退店数・率、来店客全体の満足、未対応数、不満退店、永久離脱、常連数、猫別稼働率、疲労、病気回数と病欠日数、設備購入比率、行動分布とする。売上と利益を分ける。

重点検証する戦術は、特定設備だけの購入、人気猫の酷使、不満客の切り捨て、休業、満足させず課金を続ける行動、特別成功狙いの消耗、交代連打、最終日直前の酷使である。100日期間では101日目以降の負担を無視できるため、終端の疲労・病気も報告し、より長い評価期間でも確認する。

### 8.3 自動調整の範囲

最初は「Botで自動プレイして問題を抽出し、人間が設定を変更する」。Phase 4で設定候補の探索まで自動化する。設備価格、満足補正、疲労係数などに探索範囲を設け、複数目的と複数水準の評価から候補を比較する。

最適化Botの成績を下げること自体を目的にしない。初心者の継続可能性、上達による利益差、健康と利益の両立、設備や猫の選択肢が残ることを評価する。採用閾値はゲームとして狙う難易度を決めてから設定する。AI報酬だけを変更して悪い戦術を隠さず、ゲーム内ルールと報酬係数を別々に管理する。

## 9. Gymnasiumを想定したUI非依存設計

### 9.1 層の分離

```text
人間UI ─────────────┐
固定ルール／学習済み店長AI ─┤ 同じ操作コマンド
                         ↓
                  SimulationCore
                  ├─ 猫方策への行動問い合わせ
                  ├─ 状態遷移・時計・料金・健康
                  └─ イベントログ・集計
                         ↑
              Gymnasium環境アダプター
                         ↑
                    学習・評価処理
```

提案する初期言語はPython。UIや描画エンジンを必須にせず、実時間待機、画面座標、描画フレーム数にゲーム計算を依存させない。将来別言語のUIを使う場合も、コマンドと状態スナップショットの契約を維持する。

### 9.2 環境の分割

- `CatInteractionEnv`：1匹と1人の接客を1エピソードにする。1stepで猫行動を1回処理する。
- `CafeManagementEnv`：複数日営業を1エピソードにする。猫AIは内部の固定方策として動かす。

店長環境は営業前の猫ごとのシフト選択、設備購入または営業開始、営業中の割り当て・交代・待機というフェーズを持つ。営業中の1stepは1tickで、店長コマンド1つを適用し、全接客中の猫を1回ずつ更新する。営業前の購入回数には有限上限を設け、時間を進めない無限操作を防ぐ。

Gymnasiumの基本環境は単一エージェントとして構成し、猫と店長の同時学習を1つの通常環境に押し込まない。APIは次の形に合わせる。[Gymnasium Env公式仕様](https://gymnasium.farama.org/api/env/)

```python
observation, info = env.reset(seed=seed, options=options)
observation, reward, terminated, truncated, info = env.step(action)
```

`action_space` と `observation_space` を宣言し、観測は常に定義範囲に収める。可変数の猫・客・席は、設定上限まで埋めた固定長配列と存在フラグで表す。行動は対象IDを含むコマンドの固定候補とし、フェーズ・資金・健康による実行可否マスクを別途提供する。マスク対応は学習側でも実装・確認する。

猫環境の成功・不満・閉店による退店はタスク内の終了、店長環境の破産や明示した100日キャンペーン完了もタスク内の終了として `terminated=True` とする。キャンペーンの残日数は観測に含める。外部の実行上限で途中停止した場合は `truncated=True` とし、通常の閉店では長期エピソードを終了しない。[時間制限の公式説明](https://gymnasium.farama.org/tutorials/gymnasium_basics/handling_time_limits/)

### 9.3 再現性と契約

- 状態に日付、tick、猫、顧客、席、財布、待機列を含める。
- 乱数は注入し、来店・健康・方策探索を別系列にする。外生的な来店予定は事前生成し、Botの行動回数で将来客が変わらないようにする。
- 設定、seed、方策版、コマンド列、状態要約を保存し、同じ結果を再生できるようにする。
- `info` に会計内訳、報酬内訳、退店理由、診断情報を返す。非公開情報を方策入力へ流用しない。
- 無効コマンドは状態を不正更新しない。営業中は待機扱いで1tick進め、理由を記録する暫定仕様とする。
- 満席時は有限長の待機列へ入れ、待機上限超過で退店する。列上限・待機時間・不満は設定値とする。
- 同一tickの処理順は「来客生成→店長操作→猫行動→成功／失敗退店→待機期限・閉店→会計・ログ」に固定する。

## 10. 段階的な試作 Phase 1〜4

| Phase | 実装範囲 | 成果物と完了条件 |
|---|---|---|
| Phase 1：最小営業 | 猫1匹・席1つ・固定客、2種×3速度＋休む、体力・気力・満足、会計、閉店。AIは固定ルール | UIなしで1日完走。境界条件テスト、同seed再現、売上集計、行動ログを確認 |
| Phase 2：猫AI | 接客用環境、離散状態のQ学習、飽き・切り替え・特別成功、Randomと固定方策比較 | 学習・評価を分離して複数seedで比較。学習曲線と未使用条件の成績、方策保存・再読み込みを確認 |
| Phase 3：店舗と長期経営 | 複数猫・席、設備、曜日、シフト、疲労・病気、常連・不満・お気に入り、猫交代、店長環境 | 固定ルール店長で100日営業。曜日と休養が結果に影響し、二重割り当てや会計不整合がない |
| Phase 4：店長学習とバランス評価 | 店長RL、目的別Bot、水準別Bot、設定候補探索、レポート、問題プレイ再生 | 共通条件で自動比較。抜け道と初心者の破綻を報告でき、変更前後・再学習後を区別して評価できる |

Phase 1では疲労・常連・設備効果・店長RLを先に作り込まない。データ拡張点だけ用意する。Phase 2はQ表の状態数を測定してから学習し、規模が合わなければ状態を削る。Phase 4の店長学習方式は行動空間と基準Botの成績が分かってから選ぶ。

## 11. 推奨ファイル構成と検証

```text
cat_cafe_sim/
  core/          # 状態、コマンド、時間進行、会計、健康
  config/        # ゲーム定数・設備・顧客・報酬設定
  policies/      # 猫方策、店長方策、Random、固定ルール
  envs/          # CatInteractionEnv、CafeManagementEnv
  training/      # 学習とモデル保存
  evaluation/    # 共通シナリオ、指標集計、設定比較
  replay/        # ログからの再実行
  tests/         # 境界条件、不変条件、再現性
  reports/       # CSV・JSON・Markdown出力
```

最低限の検証は、体力0と満足達成の同時発生、気力が回復コストと同値／未満、閉店と成功の同時発生、退店後の重複課金防止、猫・席の二重割り当て防止、病気猫の出勤禁止、累積不満による再来店停止、休養による疲労回復、無効操作、同seed・同操作列の再現とする。

学習前には環境の入出力と終了条件を検査する。報酬が上がっただけで合格にせず、満足退店率、猫の消耗、利益など元のゲーム指標も確認する。

## 12. 実装着手時の指示

CodexはPhase 1から実装する。原案と追加提案を混同せず、暫定値は設定ファイルに集約する。まず固定ルール方策でシミュレーションを成立させ、境界処理とログを確認してから学習を追加する。

未確定事項は、新しい猫の加入、猫の成長、設備の複数併設、気力回復の厳密な境界、待機客の不満、固定費と破産条件、常連度とお気に入りの成長式、最終的なUI方式である。これらは本資料の暫定仕様で試作可能だが、製品仕様として確定扱いしない。

最終的に目指すのは、猫と客の組み合わせ、休養、設備投資に複数の有効な選択肢があり、初心者から上級者まで上達を感じられるゲームである。AI評価と人間の試遊を併用して判断する。
