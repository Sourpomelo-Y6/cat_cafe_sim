# コンテンツ制作GUIと各部屋の自動表示：相談記録

記録日：2026-10-03

## 目的と位置づけ

ローカル画像生成AI・ローカルLLMで既存の猫カフェゲームに絵と文章を付け、最終的にUnityで遊べるようにする相談を記録する。[導入・移行計画](LocalAIAndUnityRoadmap.md)の後に話し合った制作GUI、コミュニケーション行動の画像、各部屋の表示を具体化した資料である。

以下は会話の要約であり、実装済み仕様ではない。ユーザーが示した希望と、アシスタントからの提案を区別する。素材数、画面構成、採用ツールなどは、明示的に決定されたものとして扱わない。

## 1. 会話の流れ

| 順序 | ユーザーの希望・質問 | 回答として提示した方向 |
| --- | --- | --- |
| 1 | 絵や会話がないシンプルなGUIゲームへ、ローカル画像生成AI・ローカルLLMで絵と文章を付けたい。最終的にUnityで遊べるようにしたい | 事前生成素材を現行GUIで試し、任意のLLM演出、UnityからPythonへの接続、段階的なC#移植へ進む計画を作成 |
| 2 | 計画の1・2について、GUIで操作できるツールを作りたい | ゲーム本体とは別のコンテンツ制作GUIで、生成・比較・修正・採用・IDへの紐付け・書き出しを扱う案 |
| 3 | コミュニケーション行動時にも、それぞれ画像を付けたい | 行動のポーズ画像と結果・状態の差分を組み合わせ、必要な行動には専用画像を用意する案 |
| 4 | 自動で各部屋の様子を見たい。画像のお客さんは手のみなど汎用的にし、その猫の絵を表示したい | 部屋の背景に、その場所で活動している猫の画像を配置し、ゲーム状態に合わせて自動で切り替える案 |
| 5 | 今までの会話をドキュメントに残してほしい | 本資料に希望、提案、未確定事項を整理 |

## 2. ユーザーが示した希望

- ローカル画像生成AIとローカルLLMで、ゲームに絵と文章を追加できるようにしたい。
- その制作をGUIから操作できるツールを作りたい。
- コミュニケーション行動ごとに画像を付けたい。
- 各部屋の様子がゲーム進行に合わせて自動で見えるようにしたい。
- お客さんは手のみなどの汎用的な表現にして、対象の猫の絵を出したい。
- 最終的にはUnityで遊べるようにしたい。

最新の希望を踏まえると、行動の画像を一覧で見るだけでなく、部屋の中で猫が過ごしている様子として見せることが中心となる。お客さん全員の顔や立ち絵を制作することは必須ではない。

## 3. コンテンツ制作GUIの提案

### 役割

制作ツールは素材を作り、ゲームは採用された素材を表示する。まずPythonで独立した制作GUIを作り、生成処理と画面処理を分離する案を提示した。採用素材と対応データをUnityでも利用できるようにする。

| 機能 | 操作内容 |
| --- | --- |
| 対象選択 | 猫・客・背景・イベントを選び、既存設定を読み込む |
| 画像制作 | ローカル画像生成へ依頼し、候補を比較して採用する |
| 文章制作 | ローカルLLMへ依頼し、候補の比較・直接編集・採用を行う |
| 素材の対応付け | 猫ID、行動、表情、状態と採用素材を結ぶ |
| 表示確認 | 画像と文章を組み合わせ、ゲームに近い表示で確認する |
| 部屋での確認 | 背景上に猫を置き、位置・大きさ・手との接触を調整する |
| 書き出し | 採用PNG、文章JSON、画像の対応表をゲーム用に出力する |

ComfyUIについては、ワークフロー編集機能をすべて作り直すのではなく、用意したワークフローのプロンプト・参照画像・seedなどを操作する案を提示した。接続ツールとしてComfyUIとOllamaを候補にしたが、実機環境や採用モデルは未確認。

実行時LLM演出を導入する場合は、制作GUIから確定イベントを選び、生成文・応答時間・失敗時の定型文を試せるようにする。ゲーム中の生成処理は、制作画面とは別の共通処理として呼び出す。

## 4. コミュニケーション行動の画像

行動・結果・状態を分けて扱う案を提示した。

| 要素 | 会話で挙げた表現例 |
| --- | --- |
| 行動 | おもちゃで遊ぶ、近寄る、触れ合う、休む |
| 結果・反応 | 喜ぶ、興味を示す、戸惑う |
| 状態 | 元気、疲れ、落ち着いている |

これらは視覚表現の例であり、現行の交流コマンドとの対応はまだ決めていない。既存のコマンド・交流分類・実際の結果を確認してから表示用の行動キーに対応付ける。

「猫×全行動×全結果」の専用画像を最初から用意すると素材数が増えるため、共通化できる部分は組み合わせる。ポーズや接触の構図が大きく変わる場面には専用画像を追加する。

制作GUIでは、基準画像と行動画像を並べて毛色・柄・体格の一致を確認し、交流順に切り替えるプレビューを用意する案。未登録の行動は通常画像で表示する。

通常接客は既存どおり自動で進み、画像表示のために毎回停止させない。プレイヤーが猫と交流する場面では、画像と短い描写を少し長く見せる案を提示した。

## 5. 各部屋の様子を自動で表示する提案

### ゲーム状態に応じた表示

部屋の背景に、現在そこにいる猫の素材を配置する。猫の配置・活動・交流行動・状態を読み取り、対応する画像に自動で切り替える。会話で挙げた場所と表示例は以下のとおり。

| 場所の例 | 表示する様子の例 |
| --- | --- |
| 接客スペース | 猫が遊ぶ、手に近寄る、撫でられる |
| 休養スペース | 猫が丸くなる、眠る、くつろぐ |
| 療養スペース | 猫が寝床で静かに休む |

部屋名と分類は提案であり、現行ゲームに独立した部屋システムが実装済みという意味ではない。現在の出勤・休養・療養や席の状態を、どの見た目の場所へ対応させるか設計する必要がある。

「自動で様子が見える」は、まず採用済み画像をゲーム状態に合わせて自動配置・切り替えする方式として提案した。毎回の画像生成や連続アニメーションを必須とするものではない。

### お客さんは汎用的な手・腕などで表現する

猫を主役にし、お客さんの顔や全身を描く代わりに、手・腕やおもちゃを使う。客ごとの人物素材を用意せずに、猫の個体差と行動を見せられる。

基本の素材構成は「部屋背景」「猫のポーズ」「汎用の手・おもちゃ」を分ける案。ただし、撫でる・抱くなどは手と猫の接触位置がずれやすいため、**猫と汎用の手を一緒に描いた透過画像**を使う案も提示した。背景からは分離し、猫ごとに同じ構図で作る。

すべての行動で手を別素材にすることは決定していない。接触のない場面では分離素材、接触が重要な場面では一体素材という使い分けを試す。

制作GUIの部屋プレビューで、猫・行動・部屋を選び、配置位置と大きさを調整する。素材を背景へ置いたときに、猫が家具や手から浮いて見えないか確認してから採用する。

## 6. 小さく試す実装単位

会話では、希望が具体化するにつれて次の試作案を提示した。

1. 制作GUIの入口として、猫1匹の画像と紹介文を生成・編集・採用し、現行ゲームへ書き出す。
2. 行動画像の試作として、猫1匹・代表的な3行動で表示を確認する。
3. 部屋表示の試作として、接客と休養の2画面、猫1匹、通常・遊ぶ・撫でられる・眠るの4種類で完成イメージを確認する。

最新の部屋表示の希望に合わせる場合は3を視覚面の試作目標とし、1の素材制作・書き出し機能と組み合わせるのが候補となる。これらの数や画面構成はアシスタントの提案であり、ユーザーが確定した実装範囲ではない。

## 7. 維持する設計案と未確定事項

### 追加相談：最初は背景込みで試作する

ユーザーは、最初の試作では背景をなるべくシンプルにして固定し、透過素材ではなく背景込みの画像を使う方針を選択した。背景・視点・猫の大きさを揃え、行動画像を切り替えて見た目を確認する。透過素材への分離は、猫を部屋内の自由な位置へ配置する必要が出た段階で再検討する。

試作の猫種・画風は未指定。初回の見た目確認では三毛猫と柔らかい2Dイラストを仮置きし、通常・遊ぶ・撫でられる・眠るの4場面を比較する。内蔵画像生成による試作であり、ローカル生成環境やゲームへの組み込みが完了したことを意味しない。

既存計画からは、画像を事前生成・採用してゲーム中に切り替えること、AIが資金や好感度などの結果を変更しないこと、AI停止や素材欠落でも代替表示で遊べること、Unityでも素材と対応表を再利用することを引き続き推奨する。

今後の設計で決める事項：

- 各部屋を同時に見せるか、タブや選択で切り替えるか。
- 複数の猫が同じ部屋にいる場合の位置、重なり、表示数。
- 現行交流コマンドと、見た目の行動の対応。
- お客さんの手・腕の画風、差分数、一体素材を使う行動。
- 静止画切り替えだけで始めるか、簡単な動きも加えるか。
- 制作GUIの技術、生成ツール、モデル、実機性能。
- 初期素材数、文章の表示箇所、実行時LLMを含める時期。

本記録の作成ではゲームコード、素材生成、制作GUI、Unityの実装は行っていない。
