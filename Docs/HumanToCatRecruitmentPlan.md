# 猫の加入方法の案と優先度

記録日：2026-09-20 / 状態：会話の整理・未実装

猫を増やす方法についてのユーザー案と、それに対する修正・追加提案を記録する。
**ユーザー指定として、野良猫スカウトは実装負担が大きいため優先度を低くする。**
以前の「保護猫受け入れとスカウトを最初に作る」という提案は見直す。スカウトを、加入機能や22匹のクリア案を成立させるための必須条件にしない。
それ以外の具体的な加入ルール・実装順は提案段階であり、採用済み仕様とは区別する。

## 1. ユーザーが提示した加入方法

| 方法 | 提示内容 | 会話での修正・具体化案 | 優先度の整理 |
|---|---|---|---|
| 野良猫のスカウト | いろいろな場所の野良猫をサブゲームでスカウトする | 公園・商店街などへ何度か通い、警戒を解き、個性や好みを知って迎える | **低い（ユーザー指定）**。後続候補として保持 |
| ペットショップで購入 | 資金を使って猫を迎える | 名前・個性・特性などを事前に確認し、欲しい特徴の猫を計画的に選ぶ | 簡単な加入窓口の候補。受け入れと共通の処理を使う案 |
| 保護猫の受け入れ | 保護猫をカフェに迎える | 依頼から選び、設備・人気・飼育枠などの条件を満たして受け入れる | 最初の加入経路の推奨候補。初回条件は既存機能で扱える範囲に絞る案 |
| イベント加入 | イベントの発生によって猫が加わる | 常連の相談や派遣先との縁などで加入候補を提示する | イベント基盤と共通の加入処理ができた後に広げる案 |

方式ごとに「お金・時間・条件」の違いを付け、単なる名称違いではなく経営上の選択にする提案。
条件に使う設備・人気・特性などは今後の機能であり、現在使えるパラメータとして扱わない。

## 2. スカウトの内容案（低優先度で保留）

- 一度の勝負で獲得するより、何度か会って迎える方式にする。
- 初めは情報が少なく、近づく・遊ぶ・見守るなどの行動を通じて、好みや特性が分かるようにする。
- 失敗するとその日は警戒して近づけなくなる程度にし、一度の失敗で永久に会えなくなる扱いは避ける案。
- 十分に慣れた後は簡単な訪問操作でも進められるようにし、毎回サブゲームを繰り返す負担を減らす案。

場所ごとの出現条件、警戒や関係の進み方、時間消費、失敗時の扱い、訪問操作の省略方法は未決定。
内容案を残すだけとし、現段階でサブゲームや場所探索の実装には着手しない。

## 3. 追加で提案した加入経路

| 追加案 | 内容 | 全体の流れとの接続 |
|---|---|---|
| 派遣先からの紹介 | 派遣先との関係が深まると、猫を迎える話を紹介してもらえる | 派遣に資金・アイテム以外の魅力を持たせる。派遣とイベントの基盤が必要 |
| 店に通ってくる猫 | 人気や設備などをきっかけに店先へ現れ、何日か交流すると加入を選べる | 外へスカウトに行かない遊び方でも出会いを作る。交流の実装負担を踏まえて後続で検討 |
| 常連からの預かり相談 | 一定期間預かり、相性や特性を知ってから正式に迎えるか決める | 一時預かりと正式所属の管理が増えるため後続候補 |

これらはアシスタントの追加提案であり、ユーザーが提示した4経路とは区別する。
一時預かりを採用する場合は、活動への参加可否、返却、費用、22匹判定への算入を別途決める。

## 4. 加入方法に共通する設計案

- 加入はプレイヤーが選ぶ。候補の出現やイベント発生だけで、自動的に所属猫を増やさない案。
- 迎える前に、費用、分かっている個性・特性、必要条件を確認できるようにする。
- 資金0でゲームオーバーとなる方針を踏まえ、支払い後の残金も表示する。資金不足や残金0になる購入の操作可否は終了条件と合わせて仕様化する。
- 所属できる猫の数と接客席数を分ける。席に入らない猫は休養や派遣へ回せる設計とする案。
- 飼育枠を設けるかは未決定。設ける場合も、22匹のクリア案を採用するなら拡張などで到達できる必要がある。
- 加入経路が違っても、猫IDの付与・所属登録・必要な資金処理・記録・保存を共通化する案。

現行のテスト猫追加や起動時の参加猫選択は、経営中の加入機能とは別である。
前に決めた「連れ帰った子猫は外部へ預ける・譲渡したものとして費用だけを処理する」扱いを維持し、今回の加入候補や22匹へ追加しない。

## 5. 加入機能内の着手順の提案

1. 候補の確認、費用・条件の確認、加入の選択、所属と保存の共通処理を作る。
2. 安定した加入窓口として、保護猫の受け入れを最初の候補にする。購入方式との先後は仕様化時に決める。
3. 同じ処理を使ってペットショップ購入やイベント・紹介による加入へ広げる。
4. スカウトは低優先度の後続候補とする。店に通う猫との交流や一時預かりも、必要な仕組みと負担を見て判断する。

これは加入機能に取り組む段階での順序案であり、[全体計画](HumanToCatGameFlowPlan.md)の最初の実装候補である猫の詳細画面を置き換えるものではない。
価格・条件・頻度などの細かな調整は、全体の流れが固まってから行う。
